Help

Welcome

This workspace helps you review, organise, and extract information from legal documents. It brings together the main platform and the Hypothesis annotation tool so that you can search for documents, open them, review suggested coding, and export results in a structured format.

This guide explains what each part of the workspace is for, what to do step by step, and what to expect when using Hypothesis alongside the platform. Where technical details are not needed for day-to-day work, they have been kept to a minimum.

Audience: Reviewers, Researchers, Admins Main tools: Workspace + Hypothesis Main workflow: Select project → Search → Open → Review → Export

What this platform is for

The platform supports a review process in which documents are collected into projects and coded using a structured coding scheme. In many cases, the system may already show suggested values or model-generated coding. A reviewer then checks these suggestions and only acts when something needs to be rejected, corrected, or added.

In simple terms, the platform helps you do four things:

  1. Organise documents into projects so that each piece of work is grouped clearly.
  2. Search and open documents to inspect the text and any extracted information.
  3. Review coding in Hypothesis, especially where model suggestions need checking.
  4. Export the coded data for analysis in Excel, SPSS, Word, or other tools.

How to Use the Workspace

For most users, this is the most important section. The usual workflow is described below.

1) Select a Project

Before doing anything else, make sure you have selected the correct project. The selected project becomes your active workspace. Searches, document selection, coding activity, and exports will usually relate to the active project.

If the wrong project is selected, you may still be able to search and open documents, but the results, exports, or saved actions may not relate to the project you intended to work on.

2) Search Documents

Use Search Documents to find cases within the available corpus. Depending on your setup, you may be able to search by keyword, code, topic, coding source, or other filters.

The purpose of this page is to narrow down the document set to the cases you want to inspect. Search results may also reflect coding or extracted values already available for those documents.

3) Open a Document

When you open a document, you will usually see its citation, an excerpt or the document text, and any extracted code values currently available for that document. These are not always the same across documents. Some documents will show many extracted values, while others will show fewer.

If the document is part of a review workflow, this is also the point at which you may switch to Hypothesis to inspect and review annotations more closely.

4) Add Documents to a Project

If you find a document that should be part of the current project, use Add to Project. This links the document to the project so it can be included in project-level review and export workflows.

Adding a document to a project does not usually mean the document has already been fully reviewed. It simply means that it is now part of that project’s working set.

5) Review Coding

The platform can copy model suggestions and gold reference annotations into your own Hypothesis workspace for the selected project. The original model and gold groups are not exposed for editing. Your workspace is where you review, reject, correct, and add annotations.

If a copied model suggestion is correct, you do not need to accept it manually. Leaving it unchanged means it is treated as an implicit accept during export. If it is wrong, add a rejection or correction in your workspace. This keeps the review workload low and preserves the original model and gold records.

6) Export Data

Once documents have been reviewed and added to a project, you can export the extracted coding data. The export page allows you to choose the coding version, coding source, and export format.

The normal HITL export is the final reviewed dataset: human corrections and additions first, then gold references, then unchanged model suggestions as implicit accepts. Rejected suggestions and superseded model values are not included in that final output.

Quick Start

If you are new to the platform, follow these steps in order.

  1. Open the workspace and make sure you are signed in.
  2. Select the correct project from the project area.
  3. Open Search Documents and locate a case you want to review.
  4. Open the document and read the excerpt or case text.
  5. Sync your workspace so model suggestions and gold references are copied into your Hypothesis group.
  6. Open Hypothesis and review the copied suggestions in your own group.
  7. Check the coding: leave correct suggestions unchanged, and only reject, correct, or add values where needed.
  8. Return to the workspace and continue with the next document.
  9. Export data when you are ready to analyse or share the results.
Important: If you cannot see annotations in Hypothesis, first sync your workspace for the selected project. Then make sure Hypothesis is showing your personal group rather than “Public” or another group.

Understanding the Main Areas of the Platform

Dashboard / Home

The dashboard is the main starting point. It usually shows the active project, links to key actions, and shortcuts to areas such as search, projects, coding scheme, and exports.

Projects

Projects group together the documents you are working on. A project may represent a dataset, a coding task, a research question, or a review batch. Working within the correct project helps keep all related documents, coding, and exports together.

Search Documents

This is where you locate cases. Some filters may reflect the coding already available for the current search results. For example, code dropdowns may show only codes present in the currently filtered result set.

Coding Scheme

The Coding Scheme explains what each code means, what kind of information it is supposed to capture, and examples of how it may be filled. This is the reference area users should consult when unsure how to interpret or apply a code.

Extract Data

This area allows you to export structured coding data. You may see options for different versions, coding sources, and export formats such as Long CSV and Wide CSV.

Using Hypothesis for Review

Hypothesis is the annotation tool used alongside the platform. Reviewers use it to inspect highlighted text, review model suggestions, and respond where a value needs confirmation or correction.

You do not need to understand the technical setup behind Hypothesis in order to use it. What matters most is knowing how to open it, how to identify the correct group, and how to reply to model annotations appropriately.

⚠️ Critical rule: do not write in the Model Predictions group

The Model Predictions group is for viewing model-generated annotations only. Reviewers must not create annotations, edit annotations, delete annotations, or reply to threads in this group.

All human review work must be done in your assigned personal workspace group. Writing in the Model Predictions group may contaminate the model annotation layer and affect later syncing, review, and data extraction.

What you may see in Hypothesis

  • Highlighted text where the system has identified a likely relevant passage in the document.
  • Notes without highlights where the system could not reliably anchor the value to a precise quote.
  • Model-generated annotations that are intended for review rather than automatic acceptance.
  • Human replies showing confirmation, rejection, correction, or discussion.

How to identify model annotations

Model annotations may be marked by tags or wording that indicate they were created by the system rather than by a human reviewer. These markers help distinguish proposed values from reviewed values.

Depending on your setup, these may include visible tags such as source labels, model tags, run identifiers, or field names. The exact appearance may vary slightly by deployment, but the purpose is the same: to make it clear what has been suggested by the system and what still needs human review.

Remember: a model annotation is usually a suggestion for review, not a final decision. Reviewers should always check the underlying text before confirming it.

How to review model annotations

The review process is designed to be simple and consistent. A reviewer’s job is to assess whether the suggested value is supported by the document and, if not, to correct it clearly.

  1. Open the document from the workspace.
  2. Open the Hypothesis sidebar.
  3. Use the Model Predictions group only to inspect model suggestions.
  4. Switch to your personal workspace group before adding any reply, annotation, correction, or discussion.
  5. Read the model annotation and the highlighted text, if present.
  6. Compare the suggested value against the document text.
  7. Decide whether the suggestion is correct, incorrect, incomplete, or unclear.
  8. Record your review in your personal workspace group using the agreed review approach for your team.

Typical review outcomes

Outcome Meaning Typical reviewer action
Accept The suggestion is correct. Confirm it in your personal workspace using your team’s preferred review wording or tags.
Reject The suggestion is not correct. Explain what is wrong and, where possible, provide the corrected value.
Correct The idea is close, but the value needs amending. Reply with the corrected value and add a better highlight if needed.
Discuss The case is unclear or needs a second opinion. Reply in your personal workspace so the issue is visible to reviewers or admins.

Good reviewing habits

  • Always check the underlying text rather than relying only on the suggested label.
  • Check the active Hypothesis group before adding any annotation or reply.
  • Use clear replies so another reviewer can understand your reasoning later.
  • Where possible, keep discussion attached to the same annotation thread in your personal workspace.
  • Create a new annotation only if the existing one does not capture the right evidence.

Keeping your review data synced into the app

Human review data is synced into the platform from the approved Hypothesis workspace groups. To make sure your review work is captured correctly:

  • Always annotate in your assigned personal workspace group.
  • Do not annotate in the Model Predictions group.
  • Use consistent tags, values, and review wording agreed by your team.
  • Keep corrections attached to the relevant document and passage where possible.
  • If your personal workspace group is missing from the app, contact an admin before continuing review work.

What happens to older or rejected model annotations

In some workflows, the platform keeps Hypothesis tidy by showing only the latest model run while preserving a fuller audit trail elsewhere in the system. This helps reviewers focus on the current state of the work rather than being distracted by outdated suggestions.

  • Older model suggestions may be removed from view in Hypothesis.
  • Rejected model suggestions may be cleaned up after review.
  • Human comments and review history are still important for traceability.

The key point for reviewers is that not every historical model suggestion needs to remain visible in the annotation layer for the system to retain an audit trail overall.

Understanding Exports

The platform supports different export formats because users need the data in different shapes depending on what they are doing next.

Long CSV

Long CSV shows one row per document-code pair. This is the more detailed export. It is useful when you want to inspect the coding carefully, check individual extracted fields, or review how a value appears for a particular document and code combination.

Wide CSV

Wide CSV shows one row per document, with codes spread across columns. This format is usually easier for spreadsheet work and quantitative analysis because each document sits on a single row.

Long vs Wide in plain terms

Long CSV is more detailed and review-friendly.
Wide CSV is more analysis-friendly and spreadsheet-friendly.

Coding source

For normal HITL work, choose Final reviewed dataset. This export combines the reviewer’s corrections and additions with gold references and unchanged model suggestions. Separate human-only, gold-only, model-only, and all-source exports are available for audit checks and troubleshooting.

The final reviewed dataset excludes suggestions that were explicitly rejected and excludes model values that were superseded by a human correction for the same document and code.

Frequently Asked Questions

I opened a document but I cannot see annotations.

Check that you have selected a project and run Sync My Workspace. The sync copies only annotations for documents in the selected project into your personal Hypothesis group. Then check that Hypothesis is open and showing your group.

Why do some documents show more extracted codes than others?

The platform shows the extracted code values available for that specific document. Not every document will contain every code, so the set of visible codes may vary from case to case.

What is the difference between human coding and AI/model coding?

Human coding refers to values created or confirmed through human review. AI/model coding refers to values proposed by the system. Depending on the workflow, users may review model suggestions before treating them as final.

Why does the code list sometimes change when I change filters in Search Documents?

Some search filters show codes that are available only in the current filtered result set. If you narrow the results, the available code list may also narrow.

What if I think a coding value is wrong?

Review the underlying text, then reject or correct the value according to your team’s review process. If needed, raise the issue with an admin or flag it for discussion.

Can older model suggestions disappear from Hypothesis?

Yes. In some setups, the annotation layer is kept tidy so that reviewers see the latest relevant suggestions rather than every historical run.

FAQs

1) I opened the page but I can’t see any annotations.

#} {#

#} {# Make sure you selected the correct group in the Hypothesis sidebar (not “Public”). Refresh the page after switching.#} {#

2) Can we change model highlight colour (e.g., pink)?

3) Who can see model annotations?

#} {#

#} {# Anyone who is a member of the Hypothesis group where the model annotations were posted.#} {#

4) Can reviewers delete model annotations?

#} {#

#} {# Typically no. The recommended workflow is: reviewers reply with decisions and the bot deletes its own rejected/outdated annotations.#} {#

5) What happens if two reviewers disagree?

#} {#

#} {# Both can reply to the same model annotation. The thread provides a discussion and audit trail. Your backend can decide#} {# final status based on tags and policy (e.g., admin review, majority, etc.).#} {#

6) Why are some model annotations not highlighted?

#} {#

#} {# Highlighting is only created when the predicted value can be found reliably and uniquely in the document text.#} {# If it is ambiguous or not present as a unique substring, the system posts a page note instead.#} {#

7) Will running the push script multiple times create duplicates?

#} {# No. The system uses stable pred_id:... tags and document/run tags to deduplicate.#} {#
