What the JuDDGES HiTL Tool Does

The JuDDGES HiTL Tool helps researchers search, review, annotate, and extract structured data from appeal court judgments. The current local corpus contains 6,154 dated judgments from the Court of Appeal (Criminal Division) in England and Wales, dated from 4 January 2003 to 22 May 2024.

The tool supports open science by making the coding process transparent. You can inspect source documents, see the coding scheme, compare human and model coding where available, review model suggestions, and export the data used in your own project.

Corpus: 6,154 dated judgments Base coding scheme: 43 variables Main workflow: Project -> Search -> Review -> Extract

Two Ways to Use This Guide

The instructions below are written for two common users.

  1. Project creators create a project, search for documents, add documents to the project, and extract the data they need.
  2. Project reviewers join an existing project, review documents, and use the Hypothesis Tool when the project uses human-in-the-loop review.
Demo 1 covers normal project, search, coding scheme, and export use. Demo 2 covers the Hypothesis Tool and human-in-the-loop review.

Before You Start

  1. Open the JuDDGES Tool at https://juddges.org/.
  2. Create an account with your email address and your own password, or log in if you already have an account.
  3. Use the top navigation bar to move between JuDDGES, My Projects, Coding Scheme, Search Documents, Extract Data, Help, and Hypothesis Tool.

The JuDDGES homepage gives background information about the Judicial Decision Data Gathering, Encoding and Sharing project, the purpose of the tool, who it was developed for, and the research outputs that underpin the tool. The project is designed around open science principles, so the underlying data, code, and research outputs can be cited and checked.

Demo 1: Basic Use of the Tool

1. My Projects

Use My Projects to create, select, inspect, edit, or delete your projects. A project is the workspace where you collect the documents you want to study.

  1. Click Create project.
  2. Give the project a clear title.
  3. Add a short description so you and other researchers know what the project is about.
  4. After creating the project, the tool takes you to Search Documents.

If you already have a project, choose Select project or Use project. This makes the project active, so searches, added documents, review work, and exports relate to the right project.

People and Projects shows who else is using the tool and what their projects are about. This supports open science by helping researchers find related work and contact each other about collaboration or data sharing.

2. Coding Scheme

Before searching, it is useful to look at the Coding Scheme. This page shows the 43 variables that the tool was originally trained to extract.

Click View guidance for a code to see its description, possible values, and examples of how those values may appear in an appeal judgment. For normal Demo 1 use, you can ignore the show or hide inactive option.

3. Search Documents

Use Search Documents to find judgments. You can type a keyword or phrase, such as burglary, remanded into custody, plea, sentence, or appeal ground. You can also choose where to search, such as everywhere.

You can narrow results by project, by coding source, and by whether a document contains a specific code. This means you can search for a keyword and also require that the document contains a selected code.

Current local counts: 649 documents have human coding, 6,154 have model coding, 649 have both human and model coding, and 5,505 are model-only. There is also one Solr demo/index record that is not part of the dated judgment corpus.

Search results show the number of matching documents and links for opening them. Use Add all results only when you are sure the whole result set belongs in your project.

4. Open a Document

When you open a document, you see its citation, an excerpt or document text, and the codes currently available for that document. Not every document contains every code. Some documents may have no value for a code because the information is not present or the model was not confident enough to extract it.

Use Show details on a code to see whether the value came from human coding, model coding, or both. If human and model coding disagree, the tool flags this. The agreement test is deliberately strict because it can require the same raw evidence span. You should inspect the text and decide whether the disagreement matters for your research.

This is an open science feature: it lets you see the evidence behind the coding, compare human and model outputs, and make your own judgement about whether the coding is good enough for your purpose.

5. Add Documents to a Project

Click Add to Project when a document should be included in your active project. You can then return to My Projects to see the documents in that project.

6. Extract Data

When you are satisfied with the documents in your project, go to Extract Data. Choose the codes, coding source, and CSV format you need.

  • Long CSV gives one row per document-code pair. This is best for checking details.
  • Wide CSV gives one row per document, with codes as columns. This is usually best for spreadsheet analysis.
  • Final reviewed dataset is the normal HiTL export: human corrections first, then gold references, then unchanged model suggestions.

Demo 2: Human-in-the-Loop Review with Hypothesis

Human-in-the-loop review means researchers work with model suggestions instead of simply accepting them. The model can suggest values, but people check the evidence, reject wrong suggestions, correct incomplete values, and add missing annotations.

In the JuDDGES workflow, Hypothesis is used as the annotation layer. The app copies model suggestions into a project review group. Reviewers work in that group, and the app syncs trusted reviewer annotations back into the server-side reviewed dataset.

Install and Control Hypothesis

Hypothesis is a browser extension. Use it only in the selected review group for your project.

  1. Use Chrome. If you do not have it, install it from Google Chrome.
  2. Create a guest Chrome profile or a separate Chrome profile for this work. This keeps the review environment separate from your personal or work accounts.
  3. Install the Hypothesis extension from the Chrome Web Store.
  4. If Chrome asks whether the extension can read and change site data, allow it so Hypothesis can annotate web pages.
  5. For better control, open Chrome Extensions, choose Hypothesis, open site access settings, and choose When you click the extension.
The separate Chrome profile and the "When you click the extension" setting help keep Hypothesis active only when you choose to use it.

Join a Review Group and Request Access

  1. Open Hypothesis Tool in the top navigation bar.
  2. Click Join / Open Review Group and join the Hypothesis group selected for the project.
  3. Return to the tool and click Request / Manage Review Access.
  4. Enter your Hypothesis username and submit the request.
  5. An admin approves or blocks the request in the Reviewer access panel.

You can find your Hypothesis username in your Hypothesis account or profile. You only need to enter the username, for example alice. The app stores it in the form acct:alice@hypothes.is.

Joining the Hypothesis group is not the same as being trusted by the JuDDGES Tool. The server imports human review annotations only from approved reviewers. Pending, blocked, and unknown Hypothesis accounts are ignored during sync.

Sync the Project Review Group

Syncing does two things. First, it prepares the workspace by copying model suggestions and available reference annotations into the project review group. Second, it imports approved reviewer annotations from Hypothesis back into the JuDDGES Tool.

  1. Select the correct project.
  2. Open Hypothesis Tool.
  3. Open Request / Manage Review Access or Review group settings.
  4. Click Sync Project Review Group.
  5. Watch the progress messages. The sync is scoped to documents in the selected project.

The original model and gold source groups are not exposed to reviewers for editing. Suggestions are copied into the review group so reviewers can work safely without corrupting source annotations.

How to Review Model Suggestions

Situation What to do What happens in export
The model suggestion is correct Do nothing. Leave the suggestion unchanged. It is treated as an implicit accept.
The model suggestion is wrong Reply to the suggestion or annotate the evidence and add the tag review:reject. The rejected model value is excluded.
The value is close but needs correction Reply with the corrected value. If making a new annotation, add the correct field tag. The human correction takes priority over the model value.
The model missed something Create a new annotation on the right text span, enter the value, and add the correct field tag. The new human annotation is included if the reviewer is approved.

For corrections and new annotations, field tags matter. A field tag tells the app which code the annotation belongs to, for example field:ConvCourtName. Where possible, reply to an existing model suggestion because the app can then infer the field from the suggestion thread.

Good Review Habits

  • Always check that Hypothesis is using the project review group, not Public.
  • Read the underlying judgment text before accepting, rejecting, or correcting a suggestion.
  • Leave correct suggestions unchanged; do not create unnecessary accept comments.
  • Use review:reject as a tag when rejecting a suggestion.
  • Use the correct field tag when creating a new annotation.
  • Keep discussion in the same annotation thread where possible.
  • Run sync again before exporting if new review work has been added in Hypothesis.

Admin Checklist for HiTL Projects

  1. Select the project.
  2. Open Hypothesis Tool.
  3. Set or confirm the shared project review group.
  4. Share the group link with reviewers.
  5. Ask reviewers to submit review access requests with their Hypothesis usernames.
  6. Approve trusted reviewers and block users who should not contribute to the reviewed dataset.
  7. Run Sync Project Review Group to copy suggestions and import approved review annotations.
  8. Use Extract Data and choose Final reviewed dataset for the normal HiTL output.

Frequently Asked Questions

I cannot see annotations in Hypothesis.

Check that you have joined the review group, opened the Hypothesis extension, and selected the project review group in the Hypothesis sidebar. Then ask an admin to run sync, or run sync yourself if you have permission.

I submitted my Hypothesis username. Why are my annotations not imported?

Your request may still be pending. An admin must approve your Hypothesis username before your annotations are imported into the reviewed dataset.

Should I mark every correct suggestion as accepted?

No. Correct model suggestions are accepted implicitly by leaving them unchanged. Only reject, correct, or add annotations where action is needed.

What if I type the wrong tag?

The app tries to resolve known aliases, but unknown or mistyped tags may not export correctly. Use the coding scheme and field tags carefully. If possible, reply to an existing model suggestion so the field can be inferred from the suggestion.

What should I export?

For normal research use after review, choose Final reviewed dataset. Use human-only, gold-only, model-only, or all-source exports only when you are auditing or troubleshooting.
